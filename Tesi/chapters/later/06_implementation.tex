\chapter{Implementation}
\label{chap:implementation}

This chapter describes how the three parts of FlowSync are implemented: the database and the
backend, the frontend, and the AI module. Each section is written by the team member who developed
that part (Section~\ref{sec:contributions}).

\section{Data model and migrations}
\label{sec:impl-db}

The database is MySQL~8.4, and its schema is created and versioned with Flyway. It has 23 tables
and one view, grouped by the modules of the backend: security (users and roles), configuration
(domain profiles, calendars with shifts and holidays, resources, skills, unavailabilities),
orders (work orders, activities, allowed resources, precedences, setup times), planning
(requests, candidate plans, assignments), decisions, execution, audit and model versions.
Hibernate does not generate the schema: it only validates the entities against it
(\texttt{ddl-auto: validate}), so a mismatch between code and database stops the application at
startup. An applied migration is never modified; every change is a new migration.

The main design choices are the following.
\begin{itemize}
  \item \textbf{Enumerations as \texttt{VARCHAR} with a \texttt{CHECK} constraint} instead of the
        MySQL \texttt{ENUM} type: adding a value costs a one-line migration.
  \item \textbf{Timestamps in UTC} (\texttt{DATETIME(6)}, \texttt{Instant} in Java); the time
        zone is applied by the frontend. Shifts are the exception, since they are local times of
        a calendar.
  \item \textbf{JSON columns} for the problem specification, the objective weights, the KPI
        details and the audit payloads (Section~\ref{sec:persistence}). The KPIs used for sorting and
        filtering are ordinary columns.
  \item \textbf{The problem specification is stored as a snapshot} in each planning request, so a
        plan remains reproducible even if orders or resources change later. Each real request
        also becomes a potential training example.
  \item \textbf{Execution events are append-only}. The view \texttt{v\_activity\_actuals}
        compares the actual duration of each activity with the estimate of M1: in production it
        is the training set of M1.
  \item \textbf{Optimistic locking} on orders and plans, so that two planners editing the same
        plan do not overwrite each other.
\end{itemize}
A demo data set, loaded only in the development profile, reproduces the workshop of the mockups
(nine resources, four orders, a maintenance window) and creates one test user per role, with the
same names used by the mock of the frontend (\texttt{pianificatore}, \texttt{operatore},
\texttt{amministratore}). In development, MySQL runs in a Docker
container defined by a Compose file, which Spring Boot starts automatically.

\section{Backend services}
\label{sec:impl-backend}

The backend is a Spring Boot~3.5 application on Java~21, organised as a modular monolith with one
package per module.

\paragraph{Errors and API documentation.} Every error is returned in the format defined by
RFC~7807 (media type \texttt{application/\allowbreak problem+json}), including those raised by
the security filters, with a trace identifier that also appears in the logs. Input that is syntactically valid
but inconsistent returns status 422 with the list of errors (code, path, message), so that the
frontend can show each message next to its field. The API is documented with OpenAPI and Swagger
UI.

\paragraph{Security.} Authentication uses JSON Web Tokens signed with HS256, validated by the
resource server of Spring Security without additional libraries. An access token lasts 15
minutes and a refresh token 7 days; a claim distinguishes the two, so a refresh token cannot be
used to call the API. The refresh step reads the user again from the database, so a disabled
account or a changed role takes effect at the next renewal. New users register themselves, but
their account stays pending until an administrator approves it and assigns a role (ADMIN,
PLANNER or OPERATOR). The login of a pending account reveals its state only if the password is
correct, so the endpoint does not disclose information about other accounts.

\paragraph{Configuration.} Resources can be listed, created, updated and deactivated (the last
three operations are reserved to administrators). Skills and calendars feed the drop-down lists
of the frontend, with a readable summary of the shifts of each calendar. The public identifier of
a resource is its code (e.g.\ \texttt{LASER}), never the numeric key of the database.

\paragraph{Orders and process graph.} Orders can be listed (with filters on state and due date),
created, updated, cancelled and reprioritised; deleting an order only marks it as cancelled, so
the plans and the audit records that mention it remain readable. The process graph of an order
is read and replaced as a whole: the service checks that every activity has at least one mode,
each with exactly one resource, that the precedences refer to existing activities and that they
contain no cycle, and
returns each problem with its path, so the frontend can show it on the right node. The public
fields of an order include a short description and the number of its activities, which the
frontend needs to show the list without loading every graph. The domain profiles are exposed
with their default weights, in the format of the contract.

\paragraph{Tests.} The integration tests run against a real MySQL~8.4 started by Testcontainers.
They check that the migrations and the entities are consistent, the authentication flows,
registration and approval, and the permissions and error codes of the API.

\section{Frontend}
\label{sec:impl-frontend}

The frontend is a single-page application written in React~19 and TypeScript, built with Vite.
The architecture was first drawn with Angular; the team switched to React because it is the
framework its members know best, which mattered for a part developed by one person in a few
weeks. The interface is in Italian and follows the HTML mockups of all the screens, written and
reviewed before the code (Section~\ref{sec:modelling}).

\paragraph{Libraries.} PrimeReact provides the components (tables, dialogs, sliders, date
pickers), with its theme recoloured from the design tokens of the mockups; React Router handles
navigation, TanStack Query the data coming from the server, React Hook Form with Zod the forms,
and React Flow the process graph editor. A global state store is not needed: almost all the state
is server data cached by TanStack Query, and the rest is local to a page. Dates, durations and
amounts are formatted with the standard \texttt{Intl} API of the browser.

\paragraph{Structure.} The code is organised by feature, with one folder for each area of the
application (orders, planning, plans, plan review, execution, configuration, model information,
audit, authentication) and a single \texttt{api} folder that knows the URLs and the formats of
the backend. Pages never call the network directly: they use the hooks of their feature, which
use the functions of the \texttt{api} folder, so a change of the API is confined to one place.
The types of the public API (contract A) are written once in TypeScript and shared by the pages
and by the mock.

\paragraph{Mock-first development.} The frontend was developed in parallel with the backend
against a mock implemented with Mock Service Worker, which intercepts the real HTTP calls in the
browser and answers with the formats of the contracts. The mock is a small backend in its own
right: it keeps its data in memory, validates the requests and returns the same errors as the
real API (422 with the path of the wrong field, 409 for state conflicts), simulates the
asynchronous computation of the plans in stages, and records the decisions in the audit log. In
this way every page was built and tested on realistic behaviour, including errors, before the
corresponding endpoint existed. When an endpoint of the backend is ready, its mock handler is
removed and the page does not change. The requirements of the frontend that were not in the
first version of the contracts (three plans per request, interpretation of a text request,
Gantt view, alerts, operator view and others) were added to the contracts in their version 1.1.

\paragraph{Server data and errors.} Every call goes through one client, which adds the access
token and turns the error responses of the API (RFC~7807) into a typed error. The pages show a
validation error under the field indicated by its path, even inside lists (for example the
second shift of a calendar), a conflict by reloading the data, and an unavailable service with a
message and a retry button. Requests that are computed in the background are polled every
1.5~seconds until they are no longer pending, and polling stops by itself. After a decision,
the lists, the Gantt charts and the audit log in the cache are refreshed.

\paragraph{Resource Gantt chart.} The chart is developed in-house, because the free libraries are
mostly task-oriented (one row per activity), while FlowSync needs one row per resource, and the
hard part, the validation of a move, had to be written anyway. It is a CSS grid with one lane
per resource; bars are positioned in proportion to their start and duration, can be dragged in
time with a snap of fifteen minutes and from one resource to another, and are buttons, so that
they can be selected from the keyboard. The time scale comes from the backend: positions are
minutes of working time from the start of the horizon, and the conversion from the real
calendars is done on the server. The rules that decide whether a move is valid (precedences,
overlaps on the resource, unavailability, allowed resources, horizon) are written once in a
module of their own and used both by the drag and by the keyboard controls; the backend repeats
the check when a modified plan is saved.

\paragraph{Rescheduling from a report.} The rescheduling page computes the impact of a problem
on the running plan directly from the Gantt data: the activities on the stopped resource that
overlap its unavailability, the activities that depend on them through the precedences (a
breadth-first visit of the precedence graph), and the orders involved with their due dates. When
the page is opened from an alert, the event is taken from the alert and only the optional
parameters are shown (Section~\ref{sec:ui-reschedule}).

\paragraph{Authentication.} The login page calls the authentication endpoint of the backend and
keeps the token and the user in the session storage of the browser, so that a reload does not
log the user out, while closing the tab does. The token is sent with every call, and an
expired token brings the user back to the login page. The permissions of each role are declared
in one module and used by the menu and by a guard on the routes, which sends the user to the
login page or to the home page of the role; the real check remains in the backend. The
registration page and the users page of the administrator (Section~\ref{sec:ui-users}) follow
the same contract as the backend, including its error codes: a duplicate username or e-mail is
shown under its field, and the login of a pending or disabled account explains the reason. This
first version deliberately leaves out the automatic renewal of the token. The test users are the
same in the mock and in the development database.

\paragraph{Quality.} TypeScript is used in strict mode, and every change is checked by the
compiler, by a linter (oxlint) and by a formatter (Prettier). Each page was then verified in the
browser on its complete flows, including the error cases (simulated by the mock), and on the
accessibility rules of Section~\ref{sec:ui-principles}: contrast, focus, labels and errors next
to the fields, size of the targets.

\section{AI module}
\label{sec:impl-ai}

The AI module is a Python~3.12 package that uses Pydantic for the data models and
OR-Tools~\cite{ortools} for CP-SAT. Its parts follow the training pipeline of
Chapter~\ref{chap:ai}; each can be used from Python or from the command line, and writes its
results as JSON or CSV files.

\paragraph{Instance schema and converters.} The unified instance schema
(Section~\ref{sec:instance-schema}) is a set of Pydantic models; the validator returns a list of
issues with the same error codes used by the API. Two converters translate the public benchmarks
into the schema: one for the flexible job shop format (Brandimarte~\cite{brandimarte1993},
Hurink, Barnes, Dauzère-Pérès and Paulli, Fattahi, Kacem) and one for the classic job shop
(JSPLIB, which includes the Taillard instances~\cite{taillard1993}, and Demirkol). For JSPLIB the
converter also stores the best known makespan and lower bound of each instance, which are used to
measure the gap of a plan. Every converted file is validated before it is written.

\paragraph{Dispatcher and rules.} The dispatcher exposes two operations, \texttt{candidates()}
and \texttt{apply(candidate)}; a decision maker is any function that receives the dispatcher and
the candidates and returns one of them. A candidate remembers the step at which it was computed,
so applying a stale candidate is rejected. Ties are broken by completion time and then by the
order of the activities in the instance, so every result is deterministic. Each plan is then
verified by an independent feasibility checker, written without reusing the code of the
dispatcher, so that an error in the dispatcher cannot hide in the checker too.

\paragraph{Teacher and dataset.} The teacher saves one JSON file per instance with the plan, the
cost, the lower bound proven by CP-SAT, the cost of the best rule and the parameters of the run,
including the version of OR-Tools. Instances that already have a solution are skipped, so a long
run can be interrupted and resumed. Since CP-SAT with several threads is not deterministic, the
dataset is always built from the saved solutions, not by solving again. The dataset builder
writes one CSV file per split, with one row per candidate, and the manifest described in
Section~\ref{sec:dataset-construction}.

\paragraph{Tests.} Every module has unit tests, including the conversion of all the real
benchmark files, the feasibility of the plans of the rules and of the teacher, the optimality of
the teacher on small instances with a known solution, and the consistency of the dataset (exactly
one positive candidate per step, deterministic split).
