\chapter{Software architecture}
\label{chap:architecture}

This chapter presents the architecture of FlowSync: the blocks that compose the system, the
responsibility of each, the data they store and the contracts through which they communicate.
How each block is implemented is described in Chapter~\ref{chap:implementation}.

\section{Overview}
\label{sec:overview}

FlowSync is divided into four blocks, each with its own technology and responsibility
(Figure~\ref{fig:architecture}):
\begin{itemize}
  \item the \textbf{frontend}, a React web application for planners, operators and
        administrators;
  \item the \textbf{backend}, a Spring Boot application with the business logic, the security
        and the public API;
  \item the \textbf{database}, MySQL, with the operational data;
  \item the \textbf{AI} block, in Python, designed as an online \emph{inference service}
        (FastAPI) that answers planning requests, a \emph{storage} for versioned models and
        datasets, and an offline \emph{training pipeline}, of which the data part exists.
\end{itemize}

\begin{figure}[htpb]
  \centering
  \includegraphics[width=\textwidth]{architecture}
  \caption{FlowSync architecture}
  \label{fig:architecture}
\end{figure}

Three principles guided this division.
\begin{itemize}
  \item \textbf{Separation of responsibilities.} The AI is written in Python, where the
        ecosystem for machine learning and constraint programming is, while the backend is
        written in Java with Spring, which offers mature support for security, persistence and
        transactions. Each block has a clear interface and can be developed and tested by a
        different person.
  \item \textbf{The frontend never talks to the AI.} Every request goes through the backend, so
        authentication, permissions, audit and error handling are in a single place, and the AI
        service is reachable only from the internal network.
  \item \textbf{Training is separated from inference.} Training can last hours and use CP-SAT
        without time limits; inference must answer in a few seconds with a model that is already
        trained. The two never run in the same process, and they share only the published
        models.
\end{itemize}

\section{Frontend}
\label{sec:frontend}

The frontend has one module for each activity of its users:
\begin{itemize}
  \item \textbf{Auth \& Roles}: login and role-based access (administrator, planner,
        operator), with the token issued by the backend; registration and the management of
        users by the administrator;
  \item \textbf{Orders \& Process Graph}: entry of orders and editing of the graph of their
        activities and precedences;
  \item \textbf{Planning \& Gantt}: planning requests, also written in natural language,
        comparison of the three candidate plans with the ATC and EDD rules, and resource Gantt
        chart;
  \item \textbf{Plan Review}: approval, modification or rejection of a plan, and rescheduling
        of the running plan after a problem;
  \item \textbf{Execution}: recording of the actual start and end of the activities by the
        operators, and reporting of problems;
  \item \textbf{KPI Dashboard}: indicators over time and open alerts;
  \item \textbf{Model Info}: version and metrics of the active model, read-only;
  \item \textbf{Configuration} and \textbf{Audit}: master data for the administrator and the
        log of who did what, added during the design of the screens.
\end{itemize}
Two of these modules express design principles. \emph{Plan Review} implements the human in the
loop: the AI proposes, but a person always decides whether a plan is adopted. \emph{Model Info}
is read-only: the user can see which model is producing the plans, for transparency, but cannot
change it; a new model is published only by the training pipeline.

Every planning request is designed to produce \textbf{three candidate plans}, which differ in the weights of
the objectives: an \emph{economic} plan that avoids overtime at the cost of a longer schedule,
a \emph{balanced} plan computed with the weights chosen by the planner, and a \emph{fast} plan
that finishes earlier at a higher cost. Each request is also to be solved with the ATC and EDD rules,
so that the planner can compare the plans of the AI with the classical baselines
(Section~\ref{sec:elicitation}).

The architecture was first drawn with Angular as frontend framework; the implementation uses
React (Section~\ref{sec:impl-frontend}), the framework that the team knows best.

\section{Backend}
\label{sec:backend}

The backend is a \emph{modular monolith}: a single deployable application, divided into modules
with separate packages and responsibilities.
\begin{itemize}
  \item \textbf{Security}: authentication with JSON Web Tokens and authorisation by role.
  \item \textbf{Configuration}: resources, calendars, skills and domain profiles. A domain
        profile (factory, public administration, project) provides the default objective
        weights, so that the same system can be used in different contexts.
  \item \textbf{Orders \& Priority}: orders, activities, process graph and priorities.
  \item \textbf{Planning}: builds the problem specification (ProblemSpec) from the data of the
        other modules, exposes the planning API and handles rescheduling.
  \item \textbf{Decisions}: approval, modification and rejection of plans, the server side of
        Plan Review.
  \item \textbf{Execution \& KPIs}: actual execution of the activities, problem reports and
        alerts, and indicators.
  \item \textbf{Audit}: records, for each plan, the input, the model version, the output and the
        decision of the planner.
  \item \textbf{Persistence}: JPA entities and versioned migrations of the schema.
  \item \textbf{AI Client}: client of the AI service, with timeout, retry and circuit breaker.
\end{itemize}
Security, Configuration, Orders and Persistence are implemented
(Section~\ref{sec:impl-backend}); the other modules are designed but not built yet.

A planning request will follow the chain Planning $\rightarrow$ AI Client $\rightarrow$ AI service.
The key choice is that Planning sends a single, self-contained, domain-independent document: the
AI does not know the tables of the database and receives only the ProblemSpec. This decouples the
two worlds, and the same document format is used to train the models
(Section~\ref{sec:instance-schema}). The AI service is an external system that can be slow or
unavailable: the timeout and the circuit breaker planned for the AI Client will prevent a problem
of the AI from blocking the whole backend. The audit is a separate, mandatory module because, in contexts such
as public administration, every automatic decision must be justifiable: who requested it, when,
and with which model.

\section{AI service}
\label{sec:ai-service}

The AI service is designed to expose three internal endpoints, reachable only by the backend and
authenticated with a key shared between the services:
\begin{itemize}
  \item \texttt{POST /optimize}: receives a ProblemSpec and returns a PlanResult;
  \item \texttt{POST /validate}: only validates a ProblemSpec, for the editors and the tests;
  \item \texttt{GET /health}: state of the service and versions of the loaded models.
\end{itemize}
Inside, a request will go through a chain of components: validation, the context model M1, the
construction of the disjunctive graph, and the policy M2 with the dispatcher, with a fallback in
case of error or low confidence. The chain is described in Section~\ref{sec:pipeline}. A
\emph{Model Loader} will load the version of each model that is marked as active. Of these
components, the validator, the dispatcher and the dispatching rules already exist as a Python
library (Section~\ref{sec:impl-ai}); the service around them does not.

The contract of the service fixes three guarantees, which the implementation will have to
respect. If the status of the result is \emph{OK} or
\emph{FALLBACK}, the plan is feasible: precedences, capacities, availability and fixed
activities are respected, and every activity appears exactly once. If the problem has no
solution within the horizon, the status is \emph{INFEASIBLE}, with the cause among the
warnings; this is a regular answer, not an error. Finally, the service answers within the time
limit of the request, and the request identifier makes the call idempotent: a retry with the
same identifier returns the same result.

\section{Training pipeline and model storage}
\label{sec:training-pipeline}

The training pipeline runs offline and produces the models used by the AI service. Its stages
are: converters of benchmarks and event logs into a common schema, instance generator, CP-SAT
teacher, dataset builder, training of the policy M2 and of the context model M1, evaluation and
model publisher (Section~\ref{sec:imitation}). The stages up to the dataset builder are
implemented, except the converter of the event logs; training, evaluation of the models and
publisher come next. The storage will keep three kinds of versioned data: model artefacts,
training datasets, and process logs and benchmarks; today datasets and teacher solutions are
versioned files with a manifest.

A model version will be published only if the evaluation judges it not worse than the dispatching
rules ATC and EDD. Publishing a version means storing its artefact and registering it in the
database (the table already exists), with its metrics and the dataset it was trained on; at most
one version per model is active. Since every plan records the version of the models that produced it, and every model
records its dataset, each plan can be traced back to the data from which the model learned.

\section{Persistence}
\label{sec:persistence}

The operational data are stored in MySQL, in six areas that mirror the modules of the backend:
configuration data, orders and processes, plans and assignments, decisions and executions, model
metadata, and audit log. The schema is versioned together with the code through migrations, and
the backend accesses it through JPA. Two choices are worth noting. Plans, KPIs and problem
specifications are stored partly as JSON, because their structure varies between domains and
JSON avoids a schema change for each variant. The model metadata are stored in MySQL, not only in
the model storage, so that the backend and the Model Info page know which version is active
without querying the AI service. Figure~\ref{fig:er} shows the entities and their relationships,
grouped by module; the audit log and the model versions are left out because they are not linked
to the other tables by foreign keys. The tables and the design choices are described in
Section~\ref{sec:impl-db}.

\section{Contracts between components}
\label{sec:contracts}

The blocks communicate through four contracts, agreed before the implementation
(Table~\ref{tab:contracts}).

\begin{table}[htpb]
  \centering
  \small
  \begin{tabular}{@{}p{3.3cm}lll@{}}
    \toprule
    \textbf{Contract} & \textbf{Producer} & \textbf{Consumer} & \textbf{Format} \\
    \midrule
    A -- Public API          & Backend          & Frontend               & REST/JSON, JWT \\
    B -- Optimisation API    & AI service       & Backend (AI Client)    & internal REST/JSON \\
    C -- Model registration  & Model publisher  & Backend, Model Info    & database record \\
    D -- Instance schema     & Converters       & Generator, evaluation  & JSON files \\
    \bottomrule
  \end{tabular}
  \caption{Contracts between the components of FlowSync}
  \label{tab:contracts}
\end{table}

\paragraph{Common conventions.} All messages are JSON. Fields follow the conventions of each
side, \texttt{camelCase} in the public API and \texttt{snake\_case} in the AI service, and the AI
Client translates between them. In the public API, dates are in ISO-8601 with the time zone; in
the ProblemSpec, times are integer minutes from the start of the horizon, because the AI does not
handle time zones or calendars: the backend converts them into numeric availability windows.
Identifiers are opaque strings, never interpreted by the AI. Both APIs are versioned (the
\texttt{/api/v1} prefix and the \texttt{spec\_version} field), and an incompatible change
increments the major version. Errors follow RFC~7807, with an error code and a path for each
problem; the main statuses are 400 for malformed JSON, 401 and 403 for authentication and roles,
404, 409 for state conflicts (e.g.\ approving a plan already rejected), 422 for input that is
syntactically valid but inconsistent, and 503 when the AI service is unavailable.

\paragraph{A -- Public API.} The API used by the frontend covers authentication, configuration,
orders and process graph, planning, plan review, execution and KPIs, model information and audit.
Planning is \emph{asynchronous}: a new request is accepted immediately with status 202 and the
address of the request, which the frontend polls until its three plans and the comparison with
ATC and EDD are ready. In this way no HTTP request stays open while the AI computes, even when the
fallback takes longer. The plan of a request is served to the frontend already converted into the
time scale of the Gantt chart (minutes of working time from the start of the horizon), so the
calendars are interpreted in one place only, the backend. Version~1.1 of the contract (25
November 2026) added what the screens of the frontend need beyond the first draft: the
interpretation of a request written in natural language, the Gantt view and the decisions, the
rescheduling of the running plan, the alerts and problem reports, the view of the operator, and
more indicators.

\paragraph{B, C and D -- internal contracts.} The optimisation API exchanges the
\emph{ProblemSpec} (resources, jobs, activities with their modes, precedences, setups, activities
already fixed, objective weights and options such as the time limit and the fallback chain) and
the \emph{PlanResult} (status, solver, model versions, confidence, assignments, values estimated
by M1, KPIs, warnings). Model registration is a database record per published version, with its
metrics, dataset and state. The instance schema is the format shared by benchmarks, generated
instances and real requests, so that the model sees in production the same structure on which it
was trained (Section~\ref{sec:instance-schema}). The full definitions are kept in the contracts
document of the repository; contract D is implemented by the AI module, contracts B and C will be
implemented with the AI service and the model publisher.

\section{Deployment}
\label{sec:deployment}

Each block will run in its own container, and the whole system will be started with Docker
Compose: the frontend, the backend, the AI service, the database and the model storage. The
training pipeline is not part of the running system: it runs separately, possibly on a machine
with a GPU, and communicates with the system only by publishing models. Today only the database
runs in a container, which the backend starts automatically during development.
